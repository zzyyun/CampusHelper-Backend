# Incident Triage — 标准化排错流程

线上问题标准化排错流程。持续时间为从接到问题到输出完整报告。

## 输入格式

用户必须提供：
- **问题描述**：一句话描述线上现象（如"用户登录接口 502"）
- **严重度**：P0（核心功能完全不可用）/ P1（功能严重受损）/ P2（功能轻微受损）

用户可选提供：
- **证据包**：错误日志、复现步骤、最近部署版本、监控截图等

## 输出产物

执行完成后，必须输出以下内容：
1. 完整 7 步排错报告（Markdown 格式）
2. `runbook.md` 文件（记录上下文、时间线、根因、后续动作）
3. 如果有代码修复：最小 diff 的代码改动 + 验证命令

---

## 7 步排错流程

每一步完成后输出当前状态摘要（`## 状态摘要`），包含已完成步骤和下一步动作。

---

### Step 1：应急处理（5 分钟内完成）

**目标**：评估影响面，给出最稳妥的应急措施。

**执行**：
1. 分析用户提供的问题描述和严重度
2. 评估当前影响面（影响多少用户、涉及哪些服务）
3. 根据问题类型选择合适的应急措施：

| 问题类型 | 首选举措 | 回滚方法 |
|---------|---------|---------|
| 最近部署引入的缺陷 | 回滚到上一个稳定版本 | `git revert <commit>` 或 `git reset --hard <old-tag>` |
| 数据库/中间件异常 | 降级到降级模式（如读缓存+返回降级数据） | 恢复完整模式需重启服务 |
| 流量异常/过载 | 限流（降低速率或拒绝非核心请求） | 移除限流配置 |
| 配置错误 | 恢复到上一份有效配置 | `git checkout HEAD~1 -- config/*` |
| 依赖服务故障 | 熔断 + 降级返回 | 移除熔断配置 |

4. **硬要求**：应急措施必须有明确的回滚方案。在报告中写明"**回滚命令**"。

**输出**：
```markdown
## 应急处理
- 影响面：<描述>
- 措施：<具体操作>
- 回滚命令：<具体的可执行命令>
```

---

### Step 2：固化上下文

**目标**：把当前已知信息写入 `runbook.md`，确保后续排查有据可查。

**执行**：
1. 读取或创建 `runbook.md`
2. 写入以下信息：
   - **标题**：incident-<日期>-<简短描述>
   - **严重度**：P0 / P1 / P2
   - **发现时间**：时间戳
   - **服务/模块**：受影响的服务名
   - **症状**：用户描述的错误现象、错误码、超时等
   - **版本信息**：当前部署版本、最近一次部署的 commit hash
   - **时间窗**：问题从何时开始、之前最后一次正常的时间
   - **影响面**：影响用户数或请求数评估
3. 将文件写入到 `<project-root>/runbook.md`

---

### Step 3：证据包整理

**目标**：结构化整理所有线索，输出 Top 3 可能原因。

**执行**：
1. 如果用户提供了证据包，解析并结构化：
   - **错误日志**：提取关键错误行，脱敏（掩码 token/cookie/IP/手机号/邮箱）
   - **错误栈**：提取关键调用链
   - **最近变更**：列出最近 5 个 commit（`git log --oneline -5`）
2. 如果没有证据包，从以下来源主动收集：
   - 应用日志文件（`*.log`）
   - Git 最近提交（`git log --oneline -10`）
   - 检查项目中的配置文件是否有近期修改
3. 输出 Top 3 可能原因，按概率从高到低排序

**脱敏规则**：
- Token/密钥：替换为 `***TOKEN_REDACTED***`
- Cookie/Session：替换为 `***COOKIE_REDACTED***`
- IP 地址：替换为 `x.x.x.x`
- 手机号：保留前 3 后 4 位，中间替换为 `****`
- 邮箱：本地部分替换为 `***`，如 `***@example.com`

---

### Step 4：复现

**目标**：把复现步骤写成可执行命令。

**执行**：
1. 根据 Top 1 可能原因构建复现方案
2. 优先使用 `curl` 命令复现（如果是 HTTP 接口问题）
3. 如果是内部逻辑问题，编写 Go 测试函数或脚本
4. **执行复现代码，验证 3 次结果一致**
5. 如果无法复现，记录"暂未复现"及推测理由

**输出格式**：
```bash
# 复现步骤
# 1. <步骤1>
curl -X <method> <url> -d '<payload>'

# 2. <步骤2>
# ...

# 预期结果：<描述>
# 实际结果：<描述>
```

---

### Step 5：定位

**目标**：用最近变更对齐症状，定位到具体根因代码行。

**执行**：
1. **变更对齐**：查看最近涉及的服务变更（`git log --oneline -10 <受影响服务目录>`）
2. **Git Bisect**：如果有一个已知的好版本和坏版本，执行 bisect 缩小范围：
   ```bash
   git bisect start
   git bisect bad HEAD
   git bisect good <known-good-tag>
   ```
3. **补观测**：如果需要更多信息，建议添加关键日志或 metrics
4. 确认根因后，记录：
   - 根因文件：`<文件路径>:<行号>`
   - 根因描述：一句话说明

---

### Step 6：修复

**目标**：最小 diff 修复 + 回归测试 + 验证。

**执行**：
1. **最小 diff**：只修改直接导致问题的代码行，不做顺手重构、格式化、命名优化等
2. **回归测试**：运行与改动最相关的测试
3. **验证**：用 Step 4 的复现命令验证修复是否生效

**硬要求**：
- diff 行数尽量少
- 不修改无关文件
- 不改动不相关的格式或命名
- 必须提供验证命令

**输出格式**：
```diff
--- a/path/to/file.go
+++ b/path/to/file.go
@@ -x,xx +x,xx @@
- // 有问题的代码
+ // 修复后的代码
```

```bash
# 验证命令
<命令>
```

---

### Step 7：复盘

**目标**：输出根因、为什么没提前发现、后续动作。

**执行**：
1. **根因**：一句话概括
2. **为什么没提前发现**：
   - 监控缺失：需要添加什么 metrics/alert
   - 测试遗漏：需要补充什么测试用例
   - 流程不足：Code Review / 灰度 / 上线检查清单
3. **后续动作**：按 P0/P1/P2 优先级列出 TODO
4. **更新 runbook.md**：追加复盘信息

---

## 硬要求（任何时候都不得违反）

| # | 要求 | 验证方式 |
|---|------|---------|
| 1 | 应急措施必须可回滚 | 报告中必须有"回滚命令"段落 |
| 2 | 复现步骤必须能重复跑 3 次都一致 | 执行并记录 3 次结果 |
| 3 | 修复必须是最小 diff，不做顺手重构 | 只修改根因相关行，diff 中不应有无关联改动 |
| 4 | 日志中的 token/cookie/用户隐私必须脱敏 | 检查输出中是否存在未脱敏的敏感信息 |
| 5 | 每个阶段结束必须输出状态摘要 | 每步均有 `## 状态摘要` 段落 |

## 输出报告模板

最终输出必须包含以下结构：

```markdown
# Incident Report - <标题>

## Step 1: 应急处理
...
## Step 2: 固化上下文
...
## Step 3: 证据包整理
...
## Step 4: 复现
...
## Step 5: 定位
...
## Step 6: 修复
...
## Step 7: 复盘
...

## 验证结果
- [ ] 复现命令 3 次一致
- [ ] 修复验证通过
- [ ] runbook 已更新
- [ ] 敏感信息已脱敏
```

## 环境依赖

- `git`：用于查看提交历史、bisect、回滚
- `curl`：用于 HTTP 接口复现
- Go 编译环境：如需编写测试代码
- 当前目录必须是 git 仓库
