## 一、功能测试（Functional Test）

### TC-F-001：上传帖子图片（成功）
- **需求来源**：Story 1 / FR-1
- **优先级**：高
- **前置条件**：用户已登录（持有有效 JWT），MinIO 服务正常运行，请求文件为合法 JPEG 格式（<5MB）
- **测试步骤**：
  1. 构造 `POST /api/v1/files/upload` 请求，Content-Type 设为 `multipart/form-data`
  2. 表单字段添加 `file`，值为测试 JPEG 文件（2MB）
  3. 表单字段添加 `category`，值为 `post`
  4. 请求头添加 `Authorization: Bearer <token>`
  5. 发送请求
- **预期结果**：
  - HTTP 状态码：200
  - 响应 JSON 包含字段：`file_id`（正整数）、`url`（非空字符串）、`size`（文件实际大小，字节）、`content_type`（`image/jpeg`）
  - URL 可访问（MinIO 返回 200）
  - 数据库 `files` 表新增一条记录，`category` = `post`

### TC-F-004：SHA-256 去重 - 相同文件复用

- **优先级**：高

## 四、状态转换测试（State Transition Test）

### TC-ST-001：文件完整生命周期（上传 → 查询 → 删除 → 物理清理）
- **需求来源**：Story 1/3/4/5
- **优先级**：高
- **前置条件**：用户已登录，MinIO 正常，系统时间可调整（用于模拟 30 天）
- **测试步骤**：
  1. 上传文件 X，获取 file_id
  2. 查询文件 X 元数据，确认存在
  3. 软删除文件 X
  4. 查询文件 X，确认返回 404
  5. 将系统时间调整为 31 天后（或修改 deleted_at 为 31 天前）
  6. 触发系统清理任务
  7. 检查 MinIO 中文件是否被删除
- **预期结果**：
  - 步骤 2：查询成功，返回元数据
  - 步骤 4：查询返回 404（软删除后不可见）
  - 步骤 7：MinIO 中文件被物理删除

---

### TC-ST-002：上传后立即删除（快速状态转换）
- **需求来源**：Story 1/4
- **优先级**：高
- **前置条件**：用户已登录
- **测试步骤**：
  1. 上传文件 X，获取 file_id
  2. 立即调用 `DELETE /api/v1/files/{file_id}`
  3. 查询文件 X
- **预期结果**：
  - 步骤 1：上传成功，返回 200
  - 步骤 2：删除成功，返回 200
  - 步骤 3：查询返回 404

---

### TC-ST-003：重复上传同一文件 → 查询 → 删除（去重场景）
- **需求来源**：FR-3 / Story 3/4
- **优先级**：高
- **前置条件**：用户 A、用户 B 均已登录，准备相同的文件 X
- **测试步骤**：
  1. 用户 A 上传文件 X，获取 file_id_A
  2. 用户 B 上传同一文件 X，获取 file_id_B
  3. 用户 A 查询 file_id_A
  4. 用户 A 删除 file_id_A
  5. 用户 B 查询 file_id_B（应返回 404，因为已软删除）
  6. 用户 B 再次上传文件 X，获取 file_id_C
- **预期结果**：
  - 步骤 2：file_id_B = file_id_A（去重）
  - 步骤 5：查询返回 404（软删除后，file_id_A 不可见）
  - 步骤 6：file_id_C = file_id_A（即使软删除，SHA-256 记录仍在，去重仍然生效；uploader_id 更新为用户 B）

---

### TC-ST-004：软删除文件在清理前保持可恢复状态
- **需求来源**：Story 4/5
- **优先级**：中
- **前置条件**：用户已登录，已上传并软删除文件 X（deleted_at < 30 天）
- **测试步骤**：
  1. 软删除文件 X（deleted_at = 10 天前）
  2. 触发系统清理任务
  3. 检查文件记录是否存在
  4. 检查 MinIO 文件是否存在
- **预期结果**：
  - 步骤 3：数据库记录仍然存在（deleted_at < 30 天，不触发物理删除）
  - 步骤 4：MinIO 文件仍然存在
  - 说明：系统未提供恢复接口，但数据仍可恢复（通过数据库操作）

---

### TC-ST-005：多用户并发上传同一文件的竞争条件
- **需求来源**：FR-3（去重并发安全）
- **优先级**：高
- **前置条件**：5 个用户已登录，各持有相同的文件 X
- **测试步骤**：
  1. 5 个用户几乎同时发起上传文件 X 的请求
  2. 统计数据库中 SHA-256 相同的记录数
  3. 统计 MinIO 中存储的文件数
- **预期结果**：
  - 数据库中相同 SHA-256 的记录数 = 1（无重复）
  - MinIO 中相同文件仅存储 1 份
  - 所有请求返回相同的 file_id
  - 无死锁或错误

---

### TC-ST-006：文件 category 从 avatar 转换为 post（业务场景）
- **需求来源**：FR-1（category 变更场景）
- **优先级**：中
- **前置条件**：用户已登录
- **测试步骤**：
  1. 用户上传头像文件 X，category=avatar，获取 file_id_1
  2. 用户删除头像文件 X（软删除）
  3. 用户重新上传同一文件 X，category=post，获取 file_id_2
  4. 查询 file_id_1 和 file_id_2 的元数据
- **预期结果**：
  - file_id_1 = file_id_2（SHA-256 去重，复用记录）
  - 数据库记录 `category` 更新为 `post`
  - storage_key 中路径包含 `post/`（或保持原 avatar/ 路径，取决于实现）
