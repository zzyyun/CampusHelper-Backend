### 2. 边界测试

#### TC-E-001: 缓存 TTL 边界 - 恰好到期时的并发访问
- **需求来源**：Story 2 - Redis 缓存 TTL 策略
- **优先级**：高
- **前置条件**：
  - Redis 缓存 Key 已写入，TTL 设为 5 分钟
  - 准备精确计时工具
- **测试步骤**：
  1. 写入缓存并记录时间
  2. 在 TTL 恰好到期的瞬间（第 300 秒）发送并发请求
  3. 观察请求是命中缓存还是穿透到数据库
  4. 验证是否有 singleflight 防护
- **预期结果**：
  - 到期瞬间的请求不会造成数据库压力激增
  - singleflight 确保只有一个请求穿透到 DB
  - 其他并发请求等待并复用结果

#### TC-E-002: 缓存穿透防护 - 查询不存在的数据
- **需求来源**：Story 2 - Acceptance Criteria - 缓存穿透防护
- **优先级**：高
- **前置条件**：
  - Redis 缓存已启用，空值缓存 TTL 为 30 秒
  - 数据库中不存在 ID 为 999999 的帖子
- **测试步骤**：
  1. 请求 `GET /api/v1/posts/999999`（不存在的帖子）
  2. 记录第一次请求的响应时间和状态码
  3. 检查 Redis 中是否有该 Key 的空值缓存
  4. 在 30 秒内再次请求相同 ID
  5. 记录第二次请求的响应时间
  6. 等待 30 秒后第三次请求
- **预期结果**：
  - 第一次请求返回 404，Redis 中缓存了空值（TTL 30s）
  - 第二次请求从 Redis 空值缓存返回，不再查询 DB，响应更快
  - 30 秒后缓存过期，第三次请求再次查询 DB

### 4. 状态转换测试

#### TC-ST-001: 缓存状态流转 - Miss -> Loading -> Hit
- **需求来源**：Story 2 - Redis 缓存生命周期
- **优先级**：高
- **前置条件**：
  - Redis 缓存已启用，目标 Key 不存在
- **测试步骤**：
  1. 清除目标缓存 Key
  2. 发起首次请求（缓存 Miss）
  3. 验证请求从数据库加载数据
  4. 检查 Redis 中缓存已写入
  5. 发起第二次请求（缓存 Hit）
  6. 验证请求直接从 Redis 返回
- **预期结果**：
  - 首次请求：Miss -> 查询 DB -> 写入 Redis -> 返回数据
  - 第二次请求：Hit -> 直接返回 Redis 数据
  - 两次返回的数据完全一致

#### TC-ST-002: 缓存状态流转 - Hit -> Expired -> Reload
- **需求来源**：Story 2 - Redis 缓存 TTL 过期
- **优先级**：高
- **前置条件**：
  - 缓存 Key 已存在且即将过期
- **测试步骤**：
  1. 请求接口确认缓存命中（Hit）
  2. 等待缓存 TTL 到期
  3. 再次请求（Expired -> Reload）
  4. 检查是否重新从 DB 加载
  5. 验证新缓存已写入
- **预期结果**：
  - 过期前请求直接走缓存
  - 过期后请求穿透到 DB 并重建缓存
  - 重建后的缓存 TTL 重置为 5 分钟

#### TC-ST-003: 缓存状态流转 - Hit -> Write Invalidation -> Miss -> Reload
- **需求来源**：Story 2 - 写操作主动失效
- **优先级**：高
- **前置条件**：
  - 帖子列表缓存已命中
- **测试步骤**：
  1. 请求帖子列表，确认缓存命中
  2. 发布新帖子（写操作）
  3. 检查列表缓存是否被清除
  4. 再次请求帖子列表
  5. 验证新数据包含刚发布的帖子
- **预期结果**：
  - 写入操作触发缓存失效（Hit -> Invalidation）
  - 下次读取 Miss 并从 DB 重新加载
  - 新缓存包含最新数据

#### TC-ST-004: 限流状态流转 - Normal -> RateLimited -> Recovery
- **需求来源**：Story 3 - 限流状态机
- **优先级**：高
- **前置条件**：
  - 限流器已初始化
  - 全局限流 60 次/分钟/IP
- **测试步骤**：
  1. 以正常速率请求（Normal 状态）
  2. 突然以高并发超过 60 次/分钟（Normal -> RateLimited）
  3. 记录 429 响应
  4. 停止高并发请求，等待 1 分钟
  5. 恢复正常请求（RateLimited -> Recovery）
  6. 验证请求恢复正常
- **预期结果**：
  - Normal 状态：请求正常通过
  - RateLimited 状态：返回 429
  - Recovery 状态：令牌补充后请求恢复正常通过

#### TC-ST-005: 降级状态流转 - Normal -> Degraded -> Normal
- **需求来源**：Story 3 - 降级策略
- **优先级**：高
- **前置条件**：
  - 降级中间件已启用
  - CPU 阈值设为 80%
- **测试步骤**：
  1. CPU 正常时请求搜索 API（Normal 状态）
  2. 通过压力测试使 CPU > 80%（Normal -> Degraded）
  3. 请求搜索 API，验证返回兜底数据
  4. 降低 CPU 负载（Degraded -> Normal）
  5. 再次请求搜索 API，验证恢复正常
- **预期结果**：
  - Normal 状态：搜索 API 返回真实结果
  - Degraded 状态：返回缓存兜底数据，响应中标注降级
  - 恢复后：搜索 API 重新返回真实结果

#### TC-ST-006: 数据库连接池状态流转 - Idle -> Active -> Idle -> Timeout
- **需求来源**：Story 4 - 连接池生命周期
- **优先级**：中
- **前置条件**：
  - 连接池参数已配置
- **测试步骤**：
  1. 服务启动后检查连接池状态（Idle）
  2. 发送一批请求使连接变为 Active
  3. 请求完成后连接回归 Idle
  4. 等待超过 ConnMaxIdleTime（3 分钟）
  5. 检查连接是否被回收
- **预期结果**：
  - Idle -> Active：连接被请求借用
  - Active -> Idle：请求完成后连接归还
  - Idle -> Timeout：超过空闲时间连接被关闭
  - 连接池大小在合理范围内波动

#### TC-ST-007: 缓存空值状态流转 - NotExists -> NullCached -> Expired -> NotExists
- **需求来源**：Story 2 - 缓存穿透防护
- **优先级**：高
- **前置条件**：
  - 数据库中不存在 ID=999999 的帖子
  - 空值缓存 TTL 为 30 秒
- **测试步骤**：
  1. 请求不存在的帖子 ID（NotExists -> NullCached）
  2. 验证 Redis 中写入空值缓存
  3. 在 30 秒内再次请求（NullCached）
  4. 验证直接返回 404 不查 DB
  5. 等待 30 秒后请求（NullCached -> Expired -> NotExists）
  6. 验证再次查询 DB
- **预期结果**：
  - 完整经历 NotExists -> NullCached -> Expired -> NotExists 周期
  - 每个阶段行为正确
  - DB 查询次数与预期一致

#### TC-ST-008: 全链路状态流转 - 高并发下的完整请求生命周期
- **需求来源**：Story 1-5 综合验证
- **优先级**：高
- **前置条件**：
  - 全部优化措施已部署（缓存、限流、连接池优化）
  - 压测工具就绪
- **测试步骤**：
  1. 以 200 并发发送帖子列表请求
  2. 观察请求是否先经限流检查
  3. 通过限流的请求检查缓存
  4. 缓存命中的请求直接返回
  5. 缓存未命中的请求查 DB
  6. 记录全链路各环节耗时
- **预期结果**：
  - 限流检查耗时 < 1ms
  - 缓存命中请求总耗时 < 50ms
  - 缓存未命中请求总耗时 < 200ms
  - 各环节日志/TraceID 完整串联
